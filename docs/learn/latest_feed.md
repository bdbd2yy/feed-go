# 业务场景

最新视频流 + 分页加载（网格浏览 / 沉浸播放）
用户先看到最新发布的视频，可以加载更早的视频。网格模式点击“加载更多”，沉浸模式在接近末尾时自动加载。

打开页面
→ 展示最新的 12 条视频

点击“加载更多”，或在沉浸模式播放到接近列表末尾
→ 以上一批最后一条视频的时间为边界
→ 再加载更早的 12 条
→ 追加到列表后面

刷新页面
→ 时间边界重置为 0
→ 重新获取最新的 12 条

# 重要概念

- 热数据： Redis 时间线覆盖的较新视频
- 冷数据：是比这段时间线更老的视频，需要去 MySQL 查询

  watermark 就是 Redis 时间线里最老一条视频的创建时间，相当于冷热分界线。

  假设 Redis 里保存的视频时间从 今天 10:00 到今天 12:00：

  更老的视频                    Redis 时间线里的视频
  ───────────────┬─────────────────────────
      冷数据     10:00          热数据       12:00
                 ↑
              watermark

  reqTime 是这次查询的时间边界：

  • 首次加载：用当前时间。
  • 翻页加载：用上一页返回的时间游标 latestBefore。

  因此：

  reqTime = 11:00
    → 要查 11:00 之前的视频
    → Redis 还覆盖其中一部分，先查 Redis
    → 不够一页时，再去 MySQL 补足

  reqTime = 09:00
    → 要查 09:00 之前的视频
    → 已经超出 Redis 时间线覆盖范围，直接查 MySQL

  reqTime == watermark 也查 MySQL，因为查询要求严格早于游标时间；Redis 中最老的视频恰好就在这个时间，时间线里已经没有更早的记录了。

  这个判断的目的就是：浏览最近的视频时用 Redis 加速，继续往下浏览历史视频时转去数据库。

# 实现细节

两个重要参数分别对应：

• limit：每批展示多少条视频。
• latest_time：用户已经浏览到的时间位置，用来继续往历史记录里查询。

例如，第一批视频从 12:00 排到 11:00，下一批就查 11:00 之前的视频。查询条件是 create_time < latestBefore，见 backend/internal/feed/
repo.go:25。

当前 React 前端把这个接口用于“最新推荐”标签，排序逻辑实际是按发布时间从新到旧。实现位于 `frontend/src/pages/FeedPage.tsx`，使用 TanStack Query 的 `useInfiniteQuery` 保存分页结果，将 `next_time` 作为下一页的 `latest_time`。每页请求 12 条；网格模式通过按钮加载，沉浸模式在剩余约三条时自动预取，并仅挂载当前视频及前后相邻视频的播放器。
